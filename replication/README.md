# ProcuraCost Replication Package

**Model version:** 2.3.0

**Schema version:** 2

**Calibration:** `source-scenario-2026-08-28`

**Legal ruleset:** `pl-pzp-2026-2027`

**Evidence status:** deterministic outputs under declared assumptions

This package reproduces the native ProcuraCost 2.3 scenario calculations. It does
not establish that the inputs are empirically valid, that a modelled difference
was realised by an organisation, or that either workflow causes a lower cost.

## Reproduce and audit

From the repository root:

```bash
npm test
npm run recompute
npm run sweep
npm run replicate
```

- `npm test` verifies the native domain, legal resolver, process-map engine,
  decision record, exports and migration boundary.
- `npm run recompute` audits all ten canonical decision records. It checks fixed
  metadata, ordered ranges, the delta identity, neutral controls and shared
  locked legal waits.
- `npm run sweep` swaps the two alternatives in every canonical scenario. The
  totals must exchange, the central difference must negate and the outer
  envelope must reverse.
- `npm run replicate` generates the three active artefacts from the same scenario
  registry and engine used by the application.

## Native 2.3 artefacts

`npm run replicate` writes exactly:

- `outputs/built-in-scenarios.json`, the complete deterministic bundle;
- `outputs/built-in-scenarios.csv`, one stable machine row per scenario;
- `outputs/built-in-scenarios.md`, an English paper-readable rendering.

The tracked `outputs/decision-thresholds.md` file is a quarantined model 2.2.2
exception pending separately approved removal. It is not generated by
`npm run replicate`, is not an active 2.3 artefact and must not be used to
interpret model 2.3. The legacy `npm run map:legacy` command writes to standard
output only, so it cannot overwrite the active package.

The renderer is deterministic. The bundle has a fixed scenario order and no
generation timestamp. CSV uses stable machine headers, RFC-style quoting, CRLF
line endings and a terminal CRLF. The pure Markdown renderer also supports
Polish when called with the `pl` locale, while the committed active package uses
English.

## Scenario order

1. `fleet_tco_reframing`
2. `erp_transformation_discovery`
3. `logistics_service_redesign`
4. `critical_material_continuity`
5. `public_it_open_with_market_consultation`
6. `stable_private_standard_service`
7. `stable_capex_replacement`
8. `discovery_solution_codesign`
9. `catalog_calloff_control`
10. `mrp_release_control`

The catalogue call-off and MRP release scenarios are neutral controls because
their process maps are identical and no competition difference is declared.
The stable standard-service scenario is a topology control only. It separately
declares the adaptive/compliant starting alternative as having restricted
supplier access compared with open policy-qualified competition. That side is
an editable transfer assumption, not a property of the workflow label.
Scenario values migrated from the former registry
remain labelled `retained_legacy_assumption`. Attached official evidence supports
a mechanism, not those monetary values.

The first five scenarios use mechanism-specific maps. Their aggregate base-day
totals are retained from model 2.2.2, while step order, day allocation and
role-hour allocation are illustrative model 2.3 inputs. Retained support
multipliers and support-cost profiles are applied to those allocations. The
internal workflow provenance collection exposes this mixed lineage; official
cases do not supply any of the numerical allocations.

## Bundle contract

Top-level metadata includes:

- `schemaVersion`, `modelVersion`, `calibrationId` and `legalRulesetId`;
- `currency: "PLN"`;
- `deltaOperation: "formalSequential_minus_adaptiveCompliant"`;
- `rangeSemantics: "declared_ranges_not_confidence_intervals"`;
- `evidenceBoundary: "deterministic_outputs_not_empirical_estimates"`;
- the canonical `scenarioOrder`.

Each scenario includes:

- scenario identifier and the six recorded decision axes;
- independent formal/sequential and adaptive/compliant alternatives;
- central difference and outer scenario envelope;
- monetisation coverage and exact calculation anchors;
- non-monetised dimensions;
- internal workflow provenance, retained assumptions, external evidence and
  role rates;
- locked legal provenance;
- explicit native or confirmed migration metadata.

The CSV intentionally serialises nested structures into JSON cells so that no
axis, alternative, coverage or migration context is lost.

## Evidence boundary

- Reference scenarios are declared starting points, not measured case outcomes.
- Mechanism-map step and role-hour allocations are illustrative model 2.3
  inputs; retained aggregate days and support profiles are disclosed separately.
- Declared low, central and high values are not confidence intervals.
- Szucs (2024) anchors only the bounded competition-transfer stress where
  supplier access differs and the restricted alternative is explicit.
- Contract-amendment and TCO differentials are zero in the native starting
  points.
- Informal bypass is disclosed but not monetised.
- Practitioner observations, including Procurement&Beyond episode 8, are not
  calibration eligible.
- Reproducing an artefact proves code-path consistency, not empirical validity
  or legal suitability.

The immutable model 2.2.2 outputs and their original documentation live under
`archive/model-2.2.2/`. Do not regenerate or reinterpret them as active 2.3
artefacts.

## Freeze checklist

Before tagging a replication release:

1. Run `npm run lint`, `npm test`, `npm run recompute` and `npm run sweep`.
2. Run `npm run replicate` after the final model or scenario change.
3. Confirm that the three named active artefacts are present and that the
   separately tracked `decision-thresholds.md` exception retains its historical
   quarantine notice.
4. Review JSON metadata, CSV headers and all ten Markdown scenario sections.
5. Confirm that the committed outputs match a clean regeneration.
6. Confirm that every empirical anchor has source provenance and every retained
   or user-supplied value is labelled accordingly.
7. Run the production build and record any environment-specific limitation
   separately from model verification.
